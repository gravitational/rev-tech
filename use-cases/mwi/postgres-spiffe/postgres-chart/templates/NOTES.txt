PostgreSQL (bitnami/postgresql, database "demo") is starting up in
{{ .Release.Namespace }}.

It only accepts TLS connections presenting a client certificate signed by
the CA in the "{{ .Values.spiffeCABundle.secretName }}" secret (your
Teleport Workload Identity trust bundle), for the "app_user" role.

Next steps:

1. Register it as a Teleport TCP Application pointing at:
     tcp://postgres.{{ .Release.Namespace }}.svc.cluster.local:5432
   See ../teleport/app-service-teleport-config.yaml (setup.sh does this
   for you by deploying a Teleport agent).

2. Deploy ../tbot-chart to issue Workload Identity SVIDs for "app_user"
   -- clients mount that Secret and connect straight to this Service,
   no Teleport-mediated network hop required. The TCP Application
   registered in step 1 is only needed for the human/CLI path (`tsh
   vnet`), not for Workload Identity clients.

3. Run one of the clients in ../clients to do a sample transaction:
     helm install pg-client-python ../clients/python/chart
     helm install pg-client-go     ../clients/go/chart

   Or follow ../clients/cli/README.md to do it by hand.

To fetch the server CA clients use to verify Postgres itself:
  kubectl get secret {{ include "postgres.fullname" . }}-server-ca \
    -n {{ .Release.Namespace }} -o jsonpath='{.data.ca\.crt}' | base64 -d

Bitnami's chart generated its own "postgres" superuser password (unused
by this demo -- nothing connects as `postgres` over the network) into a
Secret named "postgres-postgresql" if you ever need it for `kubectl exec`
troubleshooting beyond the local-socket trust auth already allowed.
